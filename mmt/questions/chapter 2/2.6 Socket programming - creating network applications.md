With UDP, the server's receive call (`recvfrom()`) returns the datagram together with the sender's IP address and port number, which come from the packet headers. To reply, the server passes those same values to `sendto()`, because a UDP socket has no connection that remembers who the other side is.

The other options are wrong:

- **First option:** Well-known port numbers apply to servers. A client normally uses an ephemeral port assigned by the operating system, so the server can't know it in advance.
- **Second option:** `accept()` and per-client sockets are TCP behavior, and UDP has no connections. The server uses its single UDP socket for all clients.
- **Third option:** The DNS maps names to IP addresses and has no role in this. The server already has the client's address from the received datagram.

One small wording issue: the option says the values come from the "initial segment" sent by the client. For UDP the unit is a datagram, not a segment, but the idea is correct, and it is still the best answer.

**The third option, which is already selected, is the best answer of the three.**

Calling `connect()` makes the client's socket initiate a TCP connection to the specified server. This triggers the three-way handshake, and when it completes, the client's socket is connected to that server.

- **First option:** This is backwards. A TCP server never reaches out to a client. The client always initiates the connection, and the server waits with a listening socket and calls `accept()`.
- **Second option:** The first half is right, since the client does reach out to the server, but the second half is wrong. A TCP connection is strictly between two endpoints, so servers are never "added" to an existing connection.
- **Third option:** The wording is slightly loose. Strictly, the client's socket is created by the earlier `socket()` call, and `connect()` then connects that socket to the server. But it is the only option with no false claim in it, and it matches the intended meaning.
