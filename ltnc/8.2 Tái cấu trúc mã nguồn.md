## 1. Case Study – Câu chuyện mở đầu

John xem xét dự án game xe tăng và nhận thấy thiết kế lớp kém, khó bảo trì:
- Một số subclass implement **cùng hành vi** nhưng hành vi đó không được định nghĩa ở base class.
- Các method trong base class **không phù hợp** với mọi subclass → bị override thường xuyên.
- Subclass reimplementing cùng hành vi nhưng với **tên method khác nhau**.

**Kết quả sau khi refactor:** loại bỏ ~50% code, dễ đọc hơn, thêm class mới nhanh hơn.  
**Kết quả 6 tháng sau (không refactor sớm):** Dự án **thất bại** vì codebase quá phức tạp để debug.

## 2. Code Smell

> Code smell **không phải bug**, nhưng là dấu hiệu của thiết kế kém, làm chậm tốc độ phát triển và tăng rủi ro lỗi.

Các loại code smell:
- **Condition & Parameter**
- **Method**
- **Field**
- **Class / Interface**

---

## 3. Refactoring là gì?

> **Refactoring (danh từ):** Thay đổi cấu trúc nội bộ của phần mềm để dễ hiểu hơn, dễ sửa đổi hơn, **mà không thay đổi hành vi quan sát được từ bên ngoài.**

---

## 4. Các kỹ thuật Refactoring

### 🔷 Condition & Parameter

| Kỹ thuật | Vấn đề | Giải pháp |
|---|---|---|
| **Decompose Conditional** | Đoạn code điều kiện dài → khó hiểu | Tách thành các method riêng |
| **Long Parameter List** | Danh sách tham số quá dài | Gom tham số thành object |

---

### 🔷 Method Refactoring

| Kỹ thuật | Vấn đề | Giải pháp |
|---|---|---|
| **Extract Method** | Đoạn code có thể nhóm lại được | Chuyển ra method riêng, gọi lại ở chỗ cũ |
| **Inline Method** | Body của method rõ ràng hơn tên method | Thay lời gọi bằng nội dung method, xóa method đi |
| **Rename Method** | Tên method không nói lên ý định | Đổi tên method cho rõ nghĩa |
| **Pull Up Method** | Subclass có method làm việc tương tự nhau | Tạo method giống nhau rồi kéo lên superclass |
| **Replace Method with Method Object** | Method quá dài, nhiều biến local | Chuyển thành class riêng; biến local → field; tách thành nhiều method |

---

### 🔷 Field Refactoring

| Kỹ thuật | Vấn đề | Giải pháp |
|---|---|---|
| **Move Field** | Field được dùng nhiều hơn ở class khác | Tạo field ở class mới, redirect toàn bộ |
| **Replace Magic Number with Constant** | Dùng số "kỳ diệu" trong code | Thay bằng hằng số có tên rõ nghĩa |
| **Encapsulate Field** | Field public trực tiếp | Tạo getter/setter để truy cập |
| **Explaining Variable** | Biểu thức phức tạp khó hiểu | Gán vào biến có tên giải thích |
| **Push Down Field** | Field chỉ dùng ở một vài subclass | Chuyển field xuống những subclass đó |

---

### 🔷 Class / Interface Refactoring

| Kỹ thuật | Vấn đề | Giải pháp |
|---|---|---|
| **Extract Class** | Một class làm việc của hai class (vi phạm SRP) | Tạo class mới, chuyển field & method liên quan sang |
| **Replace Conditional with Polymorphism** | Điều kiện rẽ nhánh theo kiểu object | Tạo subclass tương ứng với mỗi nhánh |
| **Extract Superclass** | Hai class có field/method giống nhau | Tạo superclass chung, chuyển phần giống lên |
| **Extract Interface** | Nhiều client dùng cùng một phần interface | Tách phần đó thành interface riêng |
| **Extract Subclass** | Một class có tính năng chỉ dùng trong một số trường hợp | Tạo subclass cho các trường hợp đó |
